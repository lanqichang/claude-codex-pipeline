# 流水线 · 操作手册（需要时查，不必每次读）

## 一、cxp 命令全表

`cxp` = `~/.local/bin/cxp` → `<skill目录>/scripts/codex_dispatch.py`，由 `scripts/install.sh` 建立。

| 命令 | 作用 |
|---|---|
| `cxp go --title 标题 --cwd 目录 --tier easy/normal/hard [选项] <<'EOF' 任务单 EOF` | 一步派单：预检 → 快照对账基线 → 执行 → 机器验收 → 失败自动返工 1 轮 → 回调 |
| `cxp fix <id> [--tier X] [--verify 命令] <<'EOF' 要点 EOF` | 返工，续接同一 Codex 会话；**自动附上上一轮全部评委报告路径**，返工单只写裁决和要点 |
| `cxp status [id] [--all]` | 查进度，每单一行（状态、档位、验收、待拍板数） |
| `cxp pending` | 列出所有待用户拍板的事项（git 提交等），收尾批量问 |
| `cxp stop [id]` | 叫停，不给 id 停全部 |
| `cxp close <id> --verdict "🟢 通过" [--archive 产出目录] [--quiet]` | 结案；`--archive` 把最新一轮评审合并存到产出目录 |
| `cxp models [--sync]` | 当前三档对应型号；`--sync` 把新模型记到 `~/.config/codex-pipeline/tiers.json`（有这份就优先用它，不改 skill 自带的默认配置） |
| `cxp check` | 体检（go 已内置） |

`go` 常用选项：

- `--verify "命令"`：脚本在工作目录独立跑。**能写就写**，它决定了要不要请评委、要不要自动返工。
- `--protect "test_*.py"`：受保护文件（验收依赖的测试或检查脚本），被改即判验收失败，防止 Codex 改测试骗过验收。
- `--allow "src/**"`：可改范围，超出的改动在评审包里标 ⚠️。
- `--readonly`：侦察单，只读，默认轻快档，不派评委。
- `--net`：联网单（抓网页、下载、调接口），工作区可写并允许联网；只读不提交。
- `--browser`：浏览器单（含联网），放开沙箱以便启动本机 Chrome，用于需要登录态的查询、截图、导出；任务单写明登录态目录和可写路径。
- `--max-tier normal`：用户说「省着点」时用；`--lock-tier`：锁档不自动升。
- `--shared`：允许与其他任务共用目录（默认拦截，防止并行互相覆盖）。
- `--auto-fix 0`：关闭失败自动返工。
- `--timeout 3600`（单轮）、`--stall 900`（无动作判卡死，跑长命令时自动放宽一倍）、`--max-commands 300`。

## 二、任务单模板

```markdown
## 目标
一句话：做完之后有什么不同。

## 背景与必读
- 必读文件：路径（只列真正需要的）
- 要遵守的规范：路径（项目里的 AGENTS.md、风格指南等，Codex 也要遵守）

## 范围
- 可改：……　只读：……（原稿、定稿只读，另存新版本）　禁止：……

## 交付物
1. ……

## 验收方法
- 可执行命令或可核对标准
```

## 三、按产出类型的默认验收（写 --verify 时参考）

| 产出 | 建议验收 |
|---|---|
| 代码、脚本 | 测试命令 + `--protect` 保护已有测试；有构建就加构建命令 |
| Markdown 文档 | 小脚本核对：必含标题和小节、字数区间、无残留占位符（如 `! grep -rn "TODO" .`）、内部链接不断 |
| 文章 | 字数区间、禁用词清单（grep）、图片引用的文件存在 |
| 幻灯片 | 页数、每页必含元素的检查脚本；需要看画面时让 Codex 导出图片放进工作目录，评委直接看图 |
| 数据 | 行数、关键字段非空、和源数据抽样比对 |

确实写不出可执行验收的（纯创意文字），在任务单里写清楚核对标准，由评委把关。

## 四、监工阈值（脚本自动，指挥不轮询）

- 卡死：默认 15 分钟无新动作（跑长命令时 30 分钟）；合盖睡眠的空白不算。
- 打转：同一命令**连续** 6 次且期间没有任何文件改动。
- 命令失控：超过 300 条。超时：单轮默认 60 分钟，单次后台调用总预算 110 分钟。

## 五、并行与隔离

- 互不碰同一目录的任务可同时派；同目录默认被拦截。
- 代码项目要并行：先 `git worktree add`，每单 `--cwd` 指向自己的工作树，通过后由指挥合并。
- 文档类：Codex 只写新版本文件，不覆盖原稿；`--cwd` 尽量指向项目子目录（目录太大时脚本会跳过全量对账）。

## 六、红线与禁派清单

- **禁派清单**：`~/.config/codex-pipeline/deny.txt`，每行写一个路径片段（如 `私密资料/`、`contracts/`），`#` 开头是注释。工作目录、附加目录或任务单路径命中任一片段，脚本直接拒绝派单；清单内容也会写进给 Codex 的执行协议。**它拦的是派单位置**：工作目录设成敏感文件夹的上级目录时脚本拦不住，只剩协议里的文字约束，所以敏感文件夹的上级目录不要当工作目录。
- 薪酬、人事、病历、客户隐私等敏感资料派给 Codex 等于发给 OpenAI，先问用户。
- Codex 不做 git、部署、发布、删除、上云、发消息、付费；这些由指挥在收尾时批量请用户拍板。
- Codex 的结论涉及具体真人的能力、意愿、岗位时，只当线索，不当结论。
- 完成以评委结论和机器验收为准，不把 Codex 自报的 success 当完成。

## 七、什么时候不派单

- 一两步就能改完的小活：指挥直接改，比写任务单加两位评委更省。
- 需要和用户反复对齐声音与取舍的创作初稿：先和用户对齐，再把排版、配图、格式核对派出去。
- 只有 Claude 这边的工具（MCP、专用连接器）才能完成的写入。

## 八、过程文件

`~/.local/share/codex-pipeline/<任务id>/`（可用环境变量 `PIPELINE_HOME` 改位置）：`task.md`、`meta.json`、`baseline/`（非 git 目录的派单前副本）、`R<n>-评审包.md`、`R<n>-评审-<维度>.md`、`R<n>-events.jsonl`、`R<n>-result.json`、`R<n>-feedback.md`、`progress.json`。

## 九、环境变量

| 变量 | 作用 |
|---|---|
| `CODEX_BIN` | Codex 可执行文件的完整路径。不设时依次找 PATH 里的 `codex`、ChatGPT 桌面版自带的 Codex |
| `PIPELINE_HOME` | 过程文件目录 |
| `CODEX_DISPATCH_NO_NOTIFY` | 设为任意值则不弹系统通知 |
